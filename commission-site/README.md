# Deriv Partner Commission Dashboard

This site uses Deriv OAuth 2.0 Authorization Code + PKCE and the official application markup statistics API contract. It displays markup generated by the registered applications belonging to the authorized Deriv account.

## Official API contract

The implementation follows the official Deriv documentation:

- OAuth authorization: `https://auth.deriv.com/oauth2/auth`
- OAuth token exchange: `https://auth.deriv.com/oauth2/token`
- Application markup statistics: WebSocket v3 `app_markup_statistics`
- OAuth scope: `application_read`
- Markup totals: `total_app_markup_usd`, `total_transactions_count`, and `breakdown`

The markup request accepts `date_from` and `date_to` as inclusive `YYYY-MM-DD HH:MM:SS` values. The response is grouped by registered `app_id` and includes USD markup and transaction counts.

## Deriv developer-dashboard setup

1. Register an OAuth application in the Deriv developer dashboard.
2. Use the application ID as `DERIV_APP_ID`.
3. Register the exact callback URI used by the server:
   - Local: `http://localhost:8787/auth/callback`
   - Production: `https://your-domain.example/auth/callback`
4. Enable the `application_read` scope for the application.
5. Ensure the account has registered applications and is eligible for application markup statistics. The API may return no breakdown rows when there is no activity.

The official PKCE documentation specifies the application ID, redirect URI, `application_read` scope, state, code verifier, and S256 code challenge. It does not require a client secret in the documented authorization-code exchange. Do not add or send undocumented OAuth parameters.

## Environment variables

Copy `.env.example` to `.env` for the server process:

```env
DERIV_APP_ID=your_registered_deriv_application_id
DERIV_REDIRECT_URI=http://localhost:8787/auth/callback
PORT=8787
```

`DERIV_APP_ID` and `DERIV_REDIRECT_URI` are server configuration. Do not use `VITE_` variables for OAuth credentials or access tokens. The access and refresh tokens are held in the server's session map and referenced by an HTTP-only cookie; they are never sent to frontend JavaScript or stored in browser storage.

The official authentication documentation states that `application_read` grants markup statistics for registered applications. The PKCE exchange currently documents no client secret. If Deriv changes the registration to require a confidential client secret, add it as a server-only environment variable and update the exchange according to the current official documentation.

## Local development

```bash
npm install
cp .env.example .env
# Edit .env with your registered Deriv application ID
npm run dev:all
```

- Vite frontend: `http://localhost:5173`
- OAuth/API server: `http://localhost:8787`

The Vite development proxy forwards `/auth` and `/api` to the server.

## Vercel deployment

Import the repository into Vercel and set the project **Root Directory** to `commission-site`. The included `vercel.json` uses `npm run build`, publishes `dist`, and rewrites `/auth/*` to the OAuth serverless functions under `/api/auth/*`.

Configure these production environment variables in Vercel:

```env
DERIV_APP_ID=your_registered_deriv_application_id
DERIV_REDIRECT_URI=https://your-project.vercel.app/auth/callback
NODE_ENV=production
```

Register the exact `DERIV_REDIRECT_URI` in the Deriv developer dashboard. Do not commit `.env` or real credentials. Vercel injects these variables into serverless functions; they are not `VITE_` frontend variables.

OAuth state and tokens are encrypted into HTTP-only cookies, so this deployment does not require Redis. This is a stateless Vercel-compatible session design; frontend JavaScript cannot read the cookies.

## Local production

Build and run the same server, with `NODE_ENV=production`:

```bash
npm run build
NODE_ENV=production npm run server
```

The local server serves `dist` in production. Use HTTPS so the session cookie receives the `Secure` attribute, and register the exact HTTPS callback URI in Deriv's developer dashboard.

## Security behavior

- OAuth state is random, single-use, and expires after ten minutes.
- PKCE uses a random verifier and S256 challenge.
- Authorization-code exchange happens only on the server.
- Access and refresh tokens remain server-side.
- The session cookie is HTTP-only and SameSite=Lax.
- Logout deletes the server session and expires the cookie.
- A failed markup authorization asks the user to reauthorize. The supplied OAuth document confirms that a refresh token may be returned, but does not document a refresh-token grant request, so this app does not invent one.

## API limitations and errors

The dashboard handles invalid date ranges, empty results, unauthorized responses, rate-limit/API errors, network failures, and missing application-read access with user-visible messages. The official markup response provides total USD markup, total transactions, and a per-application breakdown. It does not provide partner sign-up or master-partner metrics; those are intentionally not displayed.
